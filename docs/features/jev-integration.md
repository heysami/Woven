# Jev integration - typed judgment for direction picking, requirement QA and DS conformance

Status: BUILT 2026-09-24 (phases 0, 1, 2, 3a, 3b, 3c, 4 harness, 5). Written
2026-09-24. See "What shipped" at the bottom for the file map, the one place
the build deviates from this plan, and what is still unverified.

Jev is TypeSafe's "System One" model: it does not generate text, it answers
typed questions about a state you give it and returns calibrated
probabilities. This plan wires it into the three decision points where Woven
currently spends a whole model turn on what is really a list of independent
judgments.

Explicitly OUT of scope: the visual verifier, the lens trio, and anything that
judges pixels. Jev has no image input, and the adapter patterns that work
around that (a vision model describes the image, Jev judges the description)
measured worse than asking the vision model directly. See "Rejected: the image
path" at the bottom for the numbers, so this does not get re-proposed.

## What Jev is, in one table

| | |
|---|---|
| endpoint | `POST https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer <key>` |
| request | `{state, model, questions: {id: Question}}` |
| `noul` | yes/no statement, optional `criteria.true/false` -> `noul` 0-1 |
| `choice` | `criteria` map option -> rubric, **max 255 options** -> `choice`, full `probabilities`, `confidence` |
| `score` | `criteria` ordered array, **2-10 levels** -> weighted `score`, `probabilities`, `legend`, `confidence` |
| context | **64k tokens total** (state + all questions), 32k for state + longest single question |
| input | **text only**, no image / audio / video |
| price | $0.042 per Mtok input, output free |
| latency | 70-500ms end to end |
| limits | 250k tok/s, 1200 req/min |

State is ingested ONCE and every question is evaluated in parallel and in
isolation, so fanning out N questions over one state is close to free. That
property is the whole reason this is worth doing.

## The jaggedness rules, encoded once

From `https://docs.typesafe.ai/model-jaggedness/jev-1.13`. Every consumer below
obeys these; they are not advisory.

1. **Literal reading.** Jev answers the question as written, not as meant.
   Every question is one clause. Boundary cases go in `criteria`.
2. **No counting.** "How many X" is unreliable and the error grows with the
   count. Fan out one question per item and sum in Python.
3. **No math, no date arithmetic.** Extract with the model, compute in code.
4. **Colour: never.** Hex values underperform English names, and Jev cannot
   reliably judge whether two hex values are near each other. All colour
   comparison stays deterministic.
5. **No indirection.** A property of a property costs accuracy. Point the
   question at the exact state field.
6. **Small state.** "Large state full of irrelevant detail" is a named failure
   mode. Send the question's own context, never the whole page.
7. **It cannot generate.** No fix text, no rewrite, no explanation. Claude
   still writes every report.

## Posture

Until Phase 4 calibration is done on real Woven data: **flag, never block.**
Gate on high-confidence FAIL only, pass everything else. A noisy judge that
never blocks but sometimes catches is useful; one that blocks gets disabled
within a week.

Every phase falls back to the Claude judgment it replaced when the key is
absent or the toggle is off. No phase is load-bearing.

## Not breaking the existing flow - the four invariants

"It falls back" is not automatically true, it is a property that has to be
designed in and tested. Two code paths that judge the same thing WILL drift
apart unless these hold. Every phase below is written to satisfy them, and
Phase 5 tests them.

**I1 - one contract, two executors.** The checklist, the criteria and the
rubric come from the SAME generated artefact in both paths. Jev criteria are
never hand-written next to a roster the preamble states differently. If
`direction-axes.jev.json` and `PROTOTYPE.md` disagree about what aesthetics
exist, the Jev path is wrong even when Jev is right.

**I2 - Jev narrows, Claude decides.** Jev's output changes what Claude
CONSIDERS, not what Claude CONCLUDES. A ranked shortlist feeding the same
option-composition step keeps both paths producing the same KIND of output,
differing only in how well informed they were. The moment code branches
straight off `probabilities` into a committed decision, the two paths are two
products.

**I3 - findings are a superset, never a different set.** Jev-on may ADD
findings; it may never remove or downgrade one the deterministic path makes.
`jev_off_findings` is always a subset of `jev_on_findings`. This is what keeps
"turn it off" a safe operation rather than a behaviour change, and it is why
3b gates only its deterministic rows.

**I4 - no silent second source of truth.** Any file Jev reads is generated by
a script from something that already exists. No new hand-maintained catalogue,
ever. A hand-copied criteria map is a guaranteed drift in three months.

### What still legitimately differs

Being honest about what the toggle DOES change, so nobody reports it as a bug:

- **Completeness.** Phase 2 judges every checklist item; the Claude path skims
  long ones. Jev-on will surface more findings on a 40-item requirement. That
  is the improvement, and by I3 it is additive.
- **Shortlist breadth.** Phase 1 with Jev weighs all 130 aesthetics; without
  it, the agent weighs what it is holding. Same composition step, wider
  candidate pool. By I2 the final pick is still Claude's.
- **Ambiguous DS findings.** `info` without Jev, `error` with a confident
  verdict. Less complete, never noisier.

Everything else must be identical, and Phase 5 asserts it.

# Phase 0 - plumbing

No behaviour change. Everything after this is additive.

**Key.** One line in `_PROVIDER_ENV_KEYS` (`editor/serve.py:1139`):

```python
"typesafe": "TH_TYPESAFE_API_KEY",
```

That picks up the existing env-then-`media-config.json` resolution and the
Settings row generation for free, exactly like every other provider.

**Endpoint.** `POST /__jev` in the daemon, proxying `api.typesafe.ai/v1/systemone`.
Copy the `/__exa/search` handler (`editor/serve.py:22770`) verbatim: the key
stays server-side and every runtime (claude / codex / opencode) reaches it with
one curl instead of needing an SDK. Retry 429 and 529 with exponential backoff
and honour `retry-after`; the official SDKs do this and we are not using one.

**Setting.** ONE global toggle in Settings, not a fourth checkbox in the
composer's Checks chip. Jev is a different execution path for checks that
already exist, not a new check. `CHAT_GUARD_OPTIONS` (`editor/app.js:12144`)
and `GUARD_DEFAULTS` (`editor/kinds/capabilities.py:698`) stay exactly as they
are, so:

- `reqQa` on + Jev on -> fast path
- `reqQa` on + Jev off -> today's behaviour
- no key -> today's behaviour, silently

**Shared helper.** `editor/jev.py`:

```
ask(state, questions, model="jev-latest") -> answers
noul_pass(answer, threshold) -> bool
choice_ranked(answer, n) -> [(id, probability), ...]
band(confidence, low, high) -> "act" | "confirm" | "escalate"
```

Stdlib `urllib` only, Python 3.9-safe (the daemon's fresh-install floor).

**Verify.** Unit test against a recorded response fixture, one live smoke call
behind the key, and `editor/check-compat.sh` before any IN USE sync.

# Phase 1 - direction picking

Self-contained. Ship first.

## The problem

When a brief states no visual direction, the agent picks from the rosters in
`PROTOTYPE.md` that are already in its preamble. That works, but it can only
weigh what it can hold, and it produces a pick rather than a ranking, so there
is no signal for "the brief genuinely does not imply an aesthetic".

## Generate the criteria, never hand-write them

Extend `scripts/build-library-indexes.py` to emit
`docs/research/direction-axes.jev.json` by scraping the four rosters already in
`PROTOTYPE.md`. Every axis fits inside the 255-option Choice cap:

| axis | heading in PROTOTYPE.md | entries |
|---|---|---|
| shell | `## Shell index` | 16 |
| style | `## Visual styles index` | 28 |
| aesthetic | `## Aesthetics index` | 130 |
| recipe | `## Recipes index` | 20 |

Each entry becomes `{id: oneLine}` lifted from the existing bullet text. One
source of truth, regenerated by script, reviewable in git. Same discipline as
the photo / illust / material indexes, and the same reason: an agent reads only
the index, so a dropped field gets replaced by confident wrong inference.

## The call

One request, five questions:

```json
{
  "state": "<the brief, plus the bound DS if any>",
  "model": "jev-latest",
  "questions": {
    "needs_direction": {"type": "noul",
      "instructions": "Does this request leave the visual direction unspecified?"},
    "recipe":    {"type": "choice", "criteria": {"...20 ids...": "...", "none": "No recipe fits"}},
    "shell":     {"type": "choice", "criteria": {"...16 ids...": "..."}},
    "style":     {"type": "choice", "criteria": {"...28 ids...": "..."}},
    "aesthetic": {"type": "choice", "criteria": {"...130 ids...": "...", "none": "No aesthetic layer"}}
  }
}
```

`needs_direction` gates the rest: a request that already states its direction
spends nothing.

## Code does the combining

A Choice returns the FULL `probabilities` map, not just the winner. So one
question per axis yields a ranked axis, and the three options are composed in
Python from the top of each axis. Recommended = highest joint probability.

If `recipe` wins at high confidence, short-circuit the axes entirely. That is
what the recipes index exists for.

**Confidence is the feature, not a nicety.** Low confidence on an axis means a
flat distribution means the brief does not imply that axis, which is the signal
to SPREAD the three options across it instead of shipping three variations of
one. That is a quality improvement, not just a speedup.

## Where it lands

`prototype/step-neg1-draft.md` and `prototype/step-neg1-emit-ui.md` gain a Jev
branch guarded on the toggle. The existing decisionTree resolution in
`prototype/step-neg1-register.md` is untouched: it already works and runs after
the axes are chosen.

## Cost and caveat

~50k tokens worst case, about $0.002, one round trip.

Write into the step file: Jev ranks on roster PROSE and cannot see the
`design-library/*-ui.png` previews the user actually chooses from. It narrows
candidates; Claude still composes the option cards and runs the recolour
pipeline.

# Phase 2 - requirement QA

The strongest fit in the plan, and it needs no new data.

## The change

`docs/agents/requirement-qa.md` keeps Steps 1 and 2 with Claude:

- Step 1: read the requirement sources FIRST and extract the flat checklist
  (TERMS / RULES / ITEMS / STATED DETAILS), each with its source location.
- Step 2: read the artefacts that shipped.

**Step 3, classify every divergence, becomes the fan-out:**

```json
{
  "state": "<the built artefact: markup, copy, data, schema>",
  "model": "jev-latest",
  "questions": {
    "req_1": {"type": "noul", "instructions": "<checklist item 1, verbatim>"},
    "req_2": {"type": "noul", "instructions": "<checklist item 2, verbatim>"}
  }
}
```

One Noul per checklist item. NEVER one global "is anything unfulfilled"
question: counting is a documented failure mode, and `sum(noul < t)` in Python
is exact.

Where a finding needs a bucket rather than a boolean, use a Choice over
`{satisfied, drift, missing, hallucination, not_applicable}` with the existing
definitions from the agent spec as the criteria.

## Routing

Three bands on confidence:

- high-confidence pass -> silent
- high-confidence fail -> goes in the report
- middle -> escalate that ONE item to a Claude read

## Why it is worth it

Forty sequential judgments inside a long subagent turn collapse to one
sub-second request. The larger gain is completeness: a long checklist today
gets skimmed, and a fan-out structurally cannot skim.

Claude still writes the report. Jev cannot generate, so the verdict prose,
the evidence locations and the auto-fix decisions all stay where they are.

# Phase 3 - design-system conformance, item by item

The phase you care most about. **Most of the win here is not Jev**, so the
sub-phases are ordered to deliver value before the key matters.

## Why it drifts today

Three mechanical reasons, all verified in the source:

1. **The rule that would catch invented components is non-gating.**
   `undefined-classes` is severity `info` (`editor/tools/qa/ds_lint.py:355`).
   That is exactly the rule that fires when a page hand-rolls `.product-card`
   instead of using the DS's `.card`. It is `info` because nothing today can
   distinguish an invented component from a legitimate page-local layout
   utility, so rather than make that call it was downgraded.

2. **ds_lint's model of the DS is a flat set of strings.** `load_ds_vocab`
   (`editor/tools/qa/ds_lint.py:185`) regex-scrapes class names and `--token`
   names into a `Set[str]`. There is no component contract (does `.card`
   require `.card__title`?), no taxonomy (component vs modifier vs utility),
   no scale intent. So `.btn` with no variant lints clean, and `--space-3`
   where the rhythm wants `--space-4` is a valid-token pass.

3. **The injected catalogue is prose, and a snapshot.**
   `_design_system_catalog` (`editor/kinds/capabilities.py:903`) embeds
   `DESIGN.md` whole with "compose ONLY from this vocabulary", and the
   preamble itself says it is "a SNAPSHOT from thread start". Prose has no
   checkable predicates, so there is no item to go through one by one.

The drift lives in the gap between VALID vocabulary (linted deterministically)
and CORRECT USE of the vocabulary (checked by nothing but a holistic read).

## 3a - the DS declares its items (no model)

Generate `design-systems/<id>/contract.json` from the DS sources. Per
component:

```json
{
  "id": "card",
  "oneLine": "Bounded content surface with optional media, title and body",
  "role": "container",
  "requiredParts": ["card__title"],
  "optionalParts": ["card__media", "card__body", "card__actions"],
  "variants": ["card--compact", "card--feature"],
  "notForUseWhen": "The content is a single interactive control; use .tile"
}
```

**This is the long pole of the whole plan** and it is independent of Jev, so
it can run in parallel with Phases 0-2. It also has to be generated rather
than hand-written per DS, or it goes stale the first time someone edits
`styles.css`.

## 3b - promote the rule (no model)

With a contract, "this page uses `.product-card`, the DS ships `.card`, and
nothing local justifies it" is deterministic. `undefined-classes` stops being
one bucket and splits by how certain the finding is:

| case | severity | needs Jev |
|---|---|---|
| undefined class whose name or structure matches a contract component | `error` | no |
| undefined class that defines chrome props on a DS component's part | `error` | no |
| undefined class with no contract match, purely positional CSS | `info` | no |
| undefined class with no contract match, chrome props, ambiguous role | `info`, or `error` when 3c is confident | **yes** |

**The last row is the trap.** The original draft of this plan said "ship 3b
before 3c, it works with the key absent" and that was wrong: the thing that
separates an invented component from legitimate page layout IS 3c. Gating the
ambiguous bucket without it would hand keyless users a wall of false failures,
which is exactly how a gate gets switched off.

So 3b gates ONLY the deterministic rows. The ambiguous row stays `info` when
Jev is unavailable and is promoted to `error` only on a confident 3c verdict.
Keyless is less complete, never noisier.

**The first two rows still close most of the drift class, with no key and no
model.**

## 3c - Jev for the one real judgment

The residue after 3b is: "is this undefined class an invented component, or
legitimate page layout?" That is a judgment, and it is one Choice.

**Pass 0 (code).** Extend the ds_lint parser to emit a flat element inventory
per page: `{page, line, tag, classes[], inlineStyle, textSample, childShape}`.
This is the one-by-one list. Deterministic.

**Pass 1 (one Jev request).** `state` is the contract. One Choice per element
over the component ids plus `page-layout-only` plus `unknown`. Code then
compares the role Jev infers against the classes actually present:

- infers `card`, has `.card` -> conforming
- infers `card` at high confidence, has `.product-card` -> drift, and the
  finding NAMES the fix
- infers `page-layout-only` -> the undefined class is legitimate, suppress

That third branch is what lets 3b gate without drowning in false positives.

**Pass 2 (Nouls, flagged set only).** One per contract rule per flagged
element: does it carry `requiredParts`, does it use a declared variant.
Combine in code.

**Budget.** A page with 300 classed elements at ~60 tokens each is ~18k tokens
of questions plus the contract as state: one request, inside the 64k budget,
~300ms, about $0.001. Shard per page for multi-page prototypes.

**Constraints specific to this phase**, from the jaggedness rules above:

- Never ask Jev about colour. `hardcoded-token-value` already does it
  deterministically via `color_to_token` and does it better.
- Never ask it to count. The fan-out is built by the parser; one element per
  question, always.
- `oneLine` and `notForUseWhen` become the Choice criteria verbatim, so vague
  contract prose yields confidently wrong role inference. This is the same
  failure as a thin library index, sharper here because this one gates.
- State is the contract plus one element's context, never the whole page.

**Ship 3a and 3b before 3c**, with 3b gating only its deterministic rows per
the table above. They work with the key absent and deliver most of the
accuracy. Jev sharpens; it does not carry.

# Phase 4 - calibrate, then trust

Do this BEFORE anything gates a build.

Take 30 prototypes with known verdicts, run Phases 2 and 3 against them, count
agreement. Set thresholds from the result, PER QUESTION TYPE, not one global
number. A DS role inference and a requirement check do not deserve the same
floor, and a destructive action deserves a higher one than a report line.

This is the step that is easy to skip and expensive to skip. The standing
caveat from the community catalogue is the right framing: schema-valid output
is not the same as a correct decision. Validate on your own data, calibrate
thresholds, keep high-impact actions behind deterministic checks.

It is cheap here precisely because every input in this plan is text. The image
path had no cheap version of this step, which is part of why it is out.

# Phase 5 - parity tests, so the two paths cannot drift

The invariants above are worthless as prose. They become real as tests in
`editor/tests/test_jev_parity.py`, run against recorded Jev fixtures so CI
needs no key and no network.

**P1 - vocabulary parity (I1, I4).** Parse the four roster headings out of
`PROTOTYPE.md`, parse `direction-axes.jev.json`, assert the id sets are
identical in both directions. Same for `contract.json` against the class set
`load_ds_vocab` scrapes: every contract component must be a real DS class.
This test failing means someone edited one source and not the generator.

**P2 - superset invariant (I3).** For N page fixtures, run ds_lint with Jev
stubbed OFF and with a recorded Jev response ON. Assert
`findings_off ⊆ findings_on` by `(rule, file, line)`, and that no finding's
severity DECREASES when Jev is on.

**P3 - decision-shape parity (I2).** For N brief fixtures, assert both paths
emit the same SHAPE: three options, each with the same required axes filled,
one marked recommended. The picks may differ; the structure may not. A Jev
path that emits two options, or an option missing a shell, is a break.

**P4 - degradation.** With the key absent, with a 401, with a 429 that
exhausts retries, and with a malformed response body: every consumer returns
the non-Jev result and logs, none raises. Model the fail-soft posture on
`run_judge` (`editor/tools/qa/visual_qa.py:375`), which already gets this
right: unavailable means `available=false` and the deterministic verdict
stands untouched.

**P5 - no preamble divergence.** Assert the capabilities preamble text for a
given project is byte-identical with the Jev toggle on and off, except for the
one block the toggle owns. The preamble is what every agent reads; an
accidental second copy of a rule there is how the two paths start building
differently.

Wire P1 into the same place `scripts/build-library-indexes.py` is already
expected to be re-run after editing a library entry, so a stale index fails
loudly rather than quietly changing what the model is offered.

## One deviation from this plan, and why

**3b's structure-match row does not gate.** This plan put "undefined class whose
name OR STRUCTURE matches a contract component" in the deterministic `error`
row. Measured against a real 26-page prototype (`projects/woven-safa`, DS
`suss`, 122 derived components), structure alone over-fires: a component's part
suffixes are generic words (`__title`, `__item`, `__logo`), so the page's
`.sidebar` scored as the DS's `.topnav` and `.paysteps` as its `.pagination` -
structurally true, semantically wrong, error-level either way. That is the wall
of false failures this plan warns gets a gate switched off.

So NAME evidence gates (suffix direction only, whole tokens: `.product-card` IS
a card, `.card-foot` is a foot belonging to one) and STRUCTURE evidence routes
to the ambiguous bucket with its suspect recorded as context, gating only on a
confident 3c verdict. That is the same logic this plan already applies to the
chrome-props row, applied to one more row. On the sample it took error-level
findings from 94 to 60 and left every genuine catch standing (`.work-card`,
`.auth-card`, `.rank-badge`, `.sub-card`, `.cell-input`).

Two smaller readings worth recording:

- **`page-layout-only` declines to PROMOTE; it never DELETES.** This plan says
  "suppress", and I3 says jev-on findings are a superset. The second wins: the
  `info` finding stays exactly where it was and Jev only withholds the
  promotion. P2 asserts it.
- **`undeclared-variant` is its own rule.** `.btn--singpass` is not a
  re-hand-rolled `.btn`; reporting it as one tells the user to delete the thing
  the page was trying to say. Different finding, different fix.

## Still unverified

- **No live call has been made.** Everything is exercised against a recorded
  fixture, a stubbed judge, and a local fake endpoint (retry-after path
  included). The request shape, the answer shape and the field names come from
  this plan, not from a response this repo has seen. The first real call is the
  thing to watch: if the wire format differs, `jev.ask` raises `JevError`, every
  consumer falls back, and the fix is local to `editor/jev.py`.
- **Phase 4 has not run.** `jev_calibrate.py` is the harness; it needs a
  labelled set built from ~30 prototypes with known verdicts. Until then the
  shipped thresholds are the conservative defaults and nothing Jev says can
  block a build.

# Rejected: the image path

Recorded so it does not get re-proposed.

**Jev cannot take an image.** Stated twice in the docs: Models says "Text only.
String, JSON object, or array of text values. No image, audio, or video
input", and State says images "are not supported (yet)".

**The workaround measured worse than not doing it.** The reference adapter
(`github.com/Alpha-Harper-Franklin/jev-multimodal`) runs a vision model first
and hands Jev the extracted evidence. Their own numbers: the compact bridge
PRESERVED direct-vision accuracy, ADDED latency, and used 1.73x the input
tokens of generic captions. They explicitly decline to claim it beats
question-conditioned captioning. For a single image, the Jev stage is dead
weight.

**The accuracy ceiling is low for QA.** Same benchmark, Qwen2.5-VL-7B over 500
images and 4,500 questions: ~87.9% on BINARY PRESENCE questions ("is there a
bicycle in this image"), ~74% on ORDINAL / rubric questions. Rubric-shaped is
exactly what "is the layout broken" and "does this match the design system"
are.

**The base rate makes it worse than the accuracy suggests.** A gate exists to
catch rare failures. 100 builds, 10 genuinely broken, judge at 88%: it catches
~9 real failures and also flags ~11 of the 90 good builds. Twenty alarms, nine
real. That ratio is why naive VLM gates get switched off.

**And Jev's confidence does not protect you.** Jev is calibrated about the TEXT
it was given, not about whether that text is true. A wrong observation is
judged confidently and correctly, and is still wrong. Two stages multiply
(~0.88 x ~0.9 = ~0.79) behind a confidence number that still reads reassuring.
It makes errors harder to see, not easier.

**What to do instead, when the time comes.** For RENDERED PAGES the exhaustive
description is not a caption, it is a render dump: every visible element's box,
resolved colours, fonts, z-index, clipping and own text, read off the CSSOM in
one `page.evaluate`. That is exact rather than approximate, it is free, and it
answers overlap, contrast, overflow, type scale and palette conformance without
a model. `preview_snapshot` today returns only url, title and `body.innerText`
(`editor/tools/qa/preview_mcp.py:347`), so this does not exist yet.

For GENERATED RASTERS with no DOM, use the `describe` skill that is already
wired (`POST /__llm_run {skill:"describe", ...}`, `editor/serve.py:24141`), and
put the QUESTIONS IN THE PROMPT rather than asking for a generic description.
A caption is written before anyone knows what will be asked, so it drops
whatever the question needed. `_vision_judge` (`editor/serve.py:17972`) is the
existing precedent for that shape.
