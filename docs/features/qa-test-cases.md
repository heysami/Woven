# QA Test Cases: plan-time test cases for interactive pieces

Status: SHIPPED (steps 1 + 2; loop closure pending)
Scope: PLATFORM-WIDE. This is a Woven capability, not a per-project tool.
It changes how every future interactive piece is planned, built, and gated,
across every family: game-experience, simulation, interactive-media,
scene-3d, motion-studio, narrative-experience, scrapbook, app-node surface,
interactive-polish. Existing projects are untouched (pieces without a
test-cases file keep today's behavior).

## Problem

The QA gate today runs a GENERIC battery (click center, one drag, one
scroll, one key) plus the art/vision lenses. Interaction crashes live in
state x input combinations (an action fired in a state its handler never
expected) and in time (minutes into a session). The plan never writes down
what should happen, so QA never checks it.

The paradigm shift: **the plan produces its own test cases, and QA walks
every one of them end to end.**

---

## 1. The artifact: `test-cases.json`

One file per interactive piece, written at research/planning time, living
next to that piece's `research.md`:

```
source/<branch>/<family-dir>/<pieceId>/test-cases.json
```

### Schema (v1)

```json
{
  "version": 1,
  "family": "<family>",
  "pieceId": "<pieceId>",
  "harness": "window.__<familyHarness>",
  "phases": ["<each state the piece can be in>"],
  "intents": ["<each action a user can take>"],
  "cases": [ <Case>, ... ],
  "matrix": { "auto": true, "exclude": [["<intent>", "<phase>"], ...] },
  "soak": { "seconds": 45, "seed": 1337, "fastForward": true }
}
```

`phases` + `intents` are the piece's committed vocabulary, whatever the
researcher committed in research.md. The runner uses them to auto-expand
the matrix (below) and to verify the runtime harness actually covers every
intent.

### Case

```json
{
  "id": "<kebab-case-id>",
  "kind": "journey | matrix | abuse | regression",
  "title": "<one sentence: the behavior under test>",
  "given": [ <steps that put the piece INTO the state under test> ],
  "steps": [ <the interaction being tested> ],
  "expect": [ <what must be true afterwards> ],
  "budgetMs": 8000
}
```

`noPageErrors` is implicit on every case even if omitted from `expect`.
`budgetMs` caps the case so a freeze fails fast instead of hanging the run.

### Step types

Reuses the five that `visual_qa.py` already executes, plus new ones:

| type      | existing? | meaning                                                    |
|-----------|-----------|------------------------------------------------------------|
| `move` `click` `drag` `scroll` `key` | yes | raw pointer/keyboard, CSS-pixel coords |
| `intent`  | NEW | `page.evaluate` -> `<harness>.injectFakeInput(intent, opts)`      |
| `eval`    | NEW | run a JS expression in the page (setup or state poke)             |
| `waitFor` | NEW | poll a JS expression until truthy, fail on timeout                |
| `tick`    | NEW | fast-forward N sim-seconds via `<harness>.tick(n)` (deterministic loops only) |
| `settle`  | NEW | plain wait, ms                                                    |
| `resize`  | NEW | viewport resize mid-case (classic crash source)                   |

### Expect types

| type            | meaning                                                        |
|-----------------|----------------------------------------------------------------|
| `noPageErrors`  | zero uncaught exceptions / unhandled rejections during the case |
| `noConsoleErrors` | zero console.error lines (allowlist regex optional)          |
| `eval` + `equals`/`in`/`truthy` | assert on live state through the harness       |
| `notBlank`      | reuse the existing blank-frame detector on a fresh screenshot  |
| `frameChanged`  | reuse the existing pixel-diff: the interaction visibly did something |

### Case kinds

- **journey**: end-to-end runs. Every piece MUST have at least: the full
  happy path start to finish, every terminal outcome reachable (not just
  the happy one), and restart-after-end.
- **matrix**: intent x phase grid, mostly AUTO-GENERATED by the runner from
  `phases` x `intents` (`matrix.auto: true`): drive the piece into each
  phase (journeys define how), inject every intent, assert `noPageErrors`.
  This is the direct answer to "fine in one state, breaks when you
  interact in another." Hand-written matrix cases only where a specific
  combination needs a specific assertion.
- **abuse**: spam (same intent 50x fast), out-of-bounds coordinates,
  malformed opts, resize mid-session, long idle, tab-hidden then visible.
  A shared library of abuse templates lives in the runner; the researcher
  only lists which apply.
- **regression**: appended AFTER a live bug is fixed. Every crash fixed in
  chat gets its reproduction written back as a case so it can never
  silently return. (Pairs with the crash-forensics ring buffer, §4.)
- **soak** (top-level block, not a case): seeded monkey run. N seconds of
  random-but-replayable intents, fast-forwarded when the loop supports
  `tick`. Catches the combinations nobody wrote down. Reproducible by seed.

## 2. Who writes it (per family)

**The family RESEARCHER writes `test-cases.json`** in the same pass that
writes `research.md`. The researcher is the one committing what the piece
IS (its states, its actions, its objective, its controls), so the cases
fall out of that commitment almost mechanically. Seams:

| family | researcher agent | typical case vocabulary |
|--------|------------------|--------------------------|
| game-experience | game-research-technique | intents x phases, win/lose journeys, spam |
| simulation | sim-research-technique | every control at min/max, pause mid-tick, long fast-forward, entity-count extremes |
| interactive-media | im-research-technique | each input granted/denied, fallback input, permission-gate journey |
| scene-3d | s3d-research-technique | pointer storm, resize, WebGL-context-lost recovery, reduced-motion, fallback ladder rungs |
| motion-studio | ms-research-technique | full scene walk forward AND backward, wheel spam, mid-transition input |
| narrative-experience | (research fleet) | full path walk, backward scroll from end, idle |
| scrapbook | scrapbook-research-technique | drag-rearrange, click-flip per cutout class, scroll journey |
| interactive-polish | polish-research-technique | hover every enriched site, scroll journey, reduced-motion |
| app-node surface | app-node-orchestrator (per graph) | every driver input kind through the logic graph |

Downstream duties:

- **Orchestrators** scaffold a `qa_cases_<pieceId>` node into
  workflow/workflow.json alongside the research node, so the cases are
  visible on canvas and re-runnable like everything else (zero daemon
  registration needed - the /__workflow merge preserves non-hash ids).
- **Builders** read the cases the same way they read research.md: each
  drawer knows up front what will be tested against its module.
- **Runtime composers** get a hardened harness contract (§4 below): the
  harness MUST be able to drive every case.
- **The plan/cost gate** shows the user the case summary with the plan
  ("N cases: j journeys, m matrix, a abuse, soak Ns") - the user approves
  what will be built AND how it will be proven.

## 3. Execution: `visual_qa.py --cases`

Extend the existing engine rather than building a new one. It already has
Playwright, pageerror + console capture, blank detection, pixel diff, the
frame strip, and the report format.

- New flag `--cases <test-cases.json>` (implies a new `mode=cases`).
- Runner loop: for each case -> fresh page load (isolation between cases)
  -> run `given` -> run `steps` -> evaluate `expect` -> record verdict.
  Matrix auto-expansion happens here (phases x intents minus excludes).
  Soak runs last.
- New step executors (`intent`, `eval`, `waitFor`, `tick`, `settle`,
  `resize`) plug into the existing `run_step` dispatch.
- Report: `report.json` gains
  `"cases": [{ "id", "verdict", "failedExpect", "pageErrors", "frames" }]`,
  plus `"casesSummary": { "pass": N, "fail": M, "soakVerdict": ... }`.
  Overall verdict = `fail` if any case fails. Exit code 6 = case failure.
- A failed case's report entry IS the reproduction recipe: the fix loop
  (solution-proposer) receives the failing case id + steps + stack, no
  guessing.
- Harness-coverage preflight: before running, evaluate that
  `<harness>.injectFakeInput` accepts every intent listed in the file; a
  missing intent is a FAIL against the runtime composer (contract
  violation), not a skip.

### Daemon endpoint

`/__qa/run` grows `&cases=1` (or auto: if a `test-cases.json` sits next to
the resolved target, cases mode is the default; the generic battery
remains the fallback for pieces without one - nothing breaks for existing
projects). The current 120s subprocess timeout becomes a per-mode budget:
cases mode gets `min(600s, sum(case budgets) + soak + slack)`.

## 4. Hardened harness contract (all runtime composers)

Every interactive family's runtime composer must expose, behind its
existing devtools harness global (`window.__game`, `__sim`, `__scene3d`,
`__ms`, ...):

```js
{
  // existing: state, loop, begin, injectFakeInput(kind, opts) ...
  intents: [...],            // MUST cover every intent in test-cases.json
  tick(nSeconds),            // deterministic fast-forward (fixed-step loops)
  snapshot(),                // small serializable state summary
  errors: [...],             // crash-forensics ring buffer (below)
}
```

Crash forensics ring buffer: a global `error` + `unhandledrejection`
handler pushes `{ message, stack, tick, phase, seed, lastIntents(<=20),
snapshot }` (keep last 10). Two payoffs: a live crash reported by the user
becomes a one-shot repro, and the fix flow appends it as a `regression`
case. Errors stay LOUD - no try/catch blankets that swallow failures into
weird-state bugs.

---

## 5. Gate wiring

At the single final QA+lens gate (all families):

1. Run `/__qa/run?...&cases=1` FIRST - it is cheap, deterministic, and
   machine-judged (no vision tokens).
2. Only if cases pass, dispatch the three lenses (craft/aesthetic/concept)
   as today.
3. On case failure -> solution-proposer receives the failing cases as
   `failures[]` entries with the case id + steps + stack -> fixPlan ->
   re-dispatch the owning drawer -> re-run ONLY the failed cases + the
   journeys (fast loop), full run again before the gate passes.

Chat-driven fixes (outside the gate): when chat fixes a crash the user hit
live, it MUST append a `regression` case to the piece's test-cases.json in
the same edit.

Platform work only - no per-project retrofit. Pieces without a
test-cases.json keep the generic battery by design.

1. **Step 1 - engine. SHIPPED.** `--cases` runner in visual_qa.py (new
   step/expect executors, matrix auto-expansion, abuse templates, seeded
   soak, harness preflight, per-case report, exit code 6; self-test fixture
   at editor/tools/qa/fixtures/cases-demo.*) + /__qa/run auto-detection
   (&cases=0 opts out) with a 600s cases-mode timeout budget.
2. **Step 2 - agent seams. SHIPPED.** All 7 family researcher mds gain the
   test-cases duty (+ codex mirror sync), all 7 runtime-composer mds carry
   the harness contract, cases-before-lenses ordering lives in the
   capabilities.py final-gate doctrine, and researchers surface the case
   summary in their hand-back for the plan gate.
3. **Later - loop closure.** Crash-forensics `errors` buffer enforcement in
   shipped runtimes, regression-append discipline in chat doctrine, a
   dedicated `qa_cases` workflow canvas node, per-family soak defaults.
